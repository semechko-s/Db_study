# Приведение логической модели к третьей нормальной форме

## 1. Цель нормализации

На этапе нормализации логическая модель PostgreSQL была проверена на соответствие первой, второй и третьей нормальным формам. Целью нормализации является устранение избыточности данных, предотвращение аномалий вставки, изменения и удаления, а также обеспечение согласованности данных.

В качестве основы использована логическая модель PostgreSQL системы сервисного центра, построенная на основе ранее разработанной концептуальной ER-модели.

В модели используются суррогатные идентификаторы `id` в качестве первичных ключей таблиц. Связи между сущностями реализуются с помощью внешних ключей.

## 2. Проверка первой нормальной формы

Модель соответствует требованиям **первой нормальной формы (1НФ)**.

Каждая таблица содержит атомарные атрибуты: одно поле хранит одно значение, отсутствуют повторяющиеся группы атрибутов и массивы значений.

Например, таблица `client` содержит отдельные атрибуты:

- `id`;
- `full_name`;
- `phone`;
- `email`.

Таблица `equipment` также содержит отдельные атомарные характеристики оборудования:

- `id`;
- `client_id`;
- `type`;
- `manufacturer`;
- `model`;
- `serial_number`;
- `condition_description`;
- `status`.

Аналогичный принцип применяется к остальным таблицам модели.

**Вывод:** все атрибуты представлены в атомарном виде, поэтому модель соответствует 1НФ.

## 3. Проверка второй нормальной формы

**Вторая нормальная форма (2НФ)** требует, чтобы таблица уже находилась в 1НФ и каждый неключевой атрибут полностью зависел от первичного ключа.

В итоговой модели в качестве первичных ключей используются отдельные атрибуты `id`. Поэтому частичные зависимости неключевых атрибутов от части составного ключа отсутствуют.

Отдельно была рассмотрена таблица `employee`. В исходном варианте атрибут `specialization` ошибочно был включён в состав первичного ключа вместе с `id`. Поскольку сотрудник однозначно определяется своим идентификатором, `specialization` не должна являться частью первичного ключа.

После исправления таблица имеет структуру:

```
employee
-------------------------
id             PK
full_name
specialization
phone
email
```

Теперь все неключевые атрибуты сотрудника зависят от `employee.id`:

```
employee.id → full_name
employee.id → specialization
employee.id → phone
employee.id → email
```

Таким образом, частичных зависимостей нет, и таблица соответствует 2НФ.

**Вывод:** после исключения `specialization` из первичного ключа таблицы модели соответствуют требованиям 2НФ.

# 4. Проверка третьей нормальной формы

**Третья нормальная форма (3НФ)** требует отсутствия транзитивных зависимостей неключевых атрибутов от первичного ключа.

При проверке модели была обнаружена транзитивная зависимость в таблице `request`.

В таблице `equipment` хранится информация о владельце оборудования:

```
equipment
-------------------------
id
client_id
...
```

Таким образом:

```
equipment.id → client_id
```

При этом заявка связана с конкретным оборудованием:

```
request.id → equipment_id
```

Следовательно, если одновременно хранить `client_id` в `request`, возникает зависимость:

```
request.id → equipment_id → client_id
```

То есть `client_id` в таблице `request` определяется не непосредственно заявкой, а через связанное с ней оборудование. Это является транзитивной зависимостью и нарушает требования 3НФ.

## 5. Устранение транзитивной зависимости

Для устранения избыточности атрибут `client_id` был удалён из таблицы `request`.

Итоговая структура заявки содержит связь с оборудованием:

```
request
-------------------------
id             PK
equipment_id   FK
operator_id    FK
created_at
received_at
description
status
waiting_reason
preliminary_cost
total_cost
client_approved
approval_at
issued_at
completed_at
```

Информация о клиенте теперь получается через связанное оборудование:

```
request
   ↓
equipment
   ↓
client
```

То есть:

```
request.equipment_id
        ↓
equipment.client_id
        ↓
client.id
```

Таким образом, информация о владельце оборудования хранится только в одном месте — в таблице `equipment`.

Это позволяет избежать ситуации, когда в `request.client_id` и `equipment.client_id` находятся разные значения для одного оборудования.

**Вывод:** удаление `client_id` из `request` устраняет транзитивную зависимость и приводит таблицу к 3НФ.

# 6. Дополнительные изменения для соответствия связям модели

В процессе проверки также были скорректированы ограничения, чтобы физическая структура PostgreSQL соответствовала кардинальностям концептуальной модели.

### Таблица `work`

В исходной версии для `work.request_id` было установлено ограничение `UNIQUE`.

Это означало бы, что для одной заявки можно создать только одну запись `work`.

Однако концептуальная модель предусматривает связь:

```
Заявка 1 : N Работа
```

и в предметной области в рамках одной заявки может выполняться несколько работ. Поэтому ограничение `UNIQUE`с `work.request_id` было удалено.

Теперь несколько работ могут ссылаться на одну заявку:

```
request 1 ───── N work
```

Это изменение не связано непосредственно с 3НФ, но необходимо для соответствия логической модели установленным кардинальностям.

### Таблица `payment`

Для `payment.request_id` было добавлено ограничение `UNIQUE`.

Концептуальная модель предусматривает:

```
Заявка 1 : 1 Оплата
```

Поэтому одна заявка должна иметь не более одной записи оплаты.

Ограничение:

```
payment.request_id UNIQUE
```

обеспечивает это требование на уровне базы данных.

# 7. Итоговая проверка 3НФ

После внесения изменений:

|Таблица / изменение|Результат|
|---|---|
|`client`|соответствует 3НФ|
|`equipment`|соответствует 3НФ|
|`request`|`client_id` удалён для устранения транзитивной зависимости|
|`employee`|`specialization` исключена из PK|
|`work`|`UNIQUE` у `request_id` удалён для реализации связи 1:N|
|`payment`|`UNIQUE` у `request_id` добавлен для реализации связи 1:1|
|`diagnosis`|соответствует 3НФ|
|`repair`|соответствует 3НФ|
|`part`|соответствует 3НФ|
|`part_reservation`|соответствует 3НФ|
|`used_part`|соответствует 3НФ|

**Итоговый вывод:**

В результате проверки и нормализации логической модели были устранены частичная зависимость в таблице `employee` и транзитивная зависимость в таблице `request`. Дополнительно ограничения уникальности были скорректированы в соответствии с кардинальностями связей предметной области. После внесённых изменений логическая модель соответствует требованиям третьей нормальной формы: каждый неключевой атрибут зависит от ключа, от всего ключа и ни от чего, кроме ключа.

# 8. Решение по намеренной денормализации

В рамках разработки логической модели было принято решение **не применять намеренную денормализацию**.

Все данные хранятся в таблицах, соответствующих их предметной области, а повторное хранение одних и тех же данных не требуется. В частности, информация о клиенте не дублируется в таблице `request`: клиент определяется через оборудование, связанное с заявкой.

Хранение `client_id` одновременно в таблицах `equipment` и `request` привело бы к дублированию данных и могло бы вызвать нарушение согласованности. Например, при изменении владельца оборудования потребовалось бы дополнительно изменять связанные заявки.

 Поэтому команда решила сохранить нормализованную структуру в 3НФ и не вводить намеренную денормализацию. Возможные проблемы производительности предполагается решать средствами PostgreSQL, в частности с помощью индексов и оптимизации запросов, а не дублированием данных.

### Вывод по денормализации

**Намеренная денормализация в текущей версии модели отсутствует.** Модель сохраняется в нормализованном виде, поскольку имеющиеся бизнес-сценарии не требуют дублирования данных для повышения производительности.

# MongoDB

# Распределение данных между PostgreSQL и MongoDB

## 1. Принцип разделения

PostgreSQL остаётся основной транзакционной базой сервисного центра. В ней лежит всё, у чего есть деньги, статусы, ограничения целостности и права доступа. MongoDB добавляется как вторая система для слабоструктурированных, вложенных и «только добавляемых» (append-only) данных.

Для каждого факта назначается **ровно один источник истины**. Если одни и те же данные встречаются в двух системах, одна из копий явно помечена как производная.

## 2. Что принадлежит PostgreSQL (источник истины)

| Таблица | Почему остаётся в PostgreSQL |
|---|---|
| `client`, `employee` | Персональные данные. Ограничение `client_contact_present`, роли и RLS из каталога `security/`. |
| `equipment` | Конкретный экземпляр техники клиента. Внешний ключ на `client`, уникальность `(manufacturer, serial_number)`, `CHECK` по статусу. |
| `request` | Жизненный цикл заявки. Более десяти `CHECK`-ограничений: `waiting_reason`, согласование клиента, даты. |
| `master_assignment` | Частичный уникальный индекс «один активный мастер на заявку». |
| `diagnosis` | Формальный факт диагностики: `UNIQUE(request_id)`, `result`, `detected_malfunction`. |
| `work`, `repair` | Стоимость и статусы работ, межтабличные инварианты. |
| `part` | Цена и остаток `stock_quantity` (`CHECK >= 0`). |
| `part_reservation`, `used_part` | Триггер `check_part_reservation_stock` с `SELECT ... FOR UPDATE` (миграция 003). Защита от двойного резервирования возможна только в ACID-транзакции. |
| `payment` | Деньги. Согласованность `amount` / `status` / `paid_at` обеспечивается ограничениями. |
| `status_history` | Аудит переходов статусов заявки. |
| `notification` | Факт уведомления и `delivery_status`. |

## 3. Что принадлежит MongoDB (источник истины)

| Коллекция | Что хранит | Источник истины для |
|---|---|---|
| `equipment_models` | Справочник моделей техники: характеристики (разные для разных типов) и типовые неисправности | Описание **модели** (не конкретного экземпляра) |
| `parts_catalog` | Описательные атрибуты запчасти, совместимость с моделями | Характеристики и совместимость запчастей |
| `diagnostic_reports` | Подробный протокол диагностики: чек-лист, измерения, найденные неисправности, вложения | Детали диагностики |
| `request_events` | Лента событий заявки: комментарии, звонки, фото, отправленные уведомления | Всё, кроме переходов статусов |

## 4. Данные «на стыке»: кто чем владеет

| Предметная область | PostgreSQL | MongoDB | Связь |
|---|---|---|---|
| **Запчасть** | `name`, `article`, `price`, `stock_quantity`, резервы и списания | `category`, `attributes`, `compatible_model_ids`, `install_notes` | `parts_catalog.pg_part_id` |
| **Оборудование** | Экземпляр: владелец, серийный номер, статус, состояние | Модель: `specs`, `common_faults` | `model_key` = `lower(manufacturer)\|lower(model)`, вычисляется приложением |
| **Диагностика** | `diagnosis`: факт, краткий `result`, `detected_malfunction` (юридически значимый итог) | Подробный протокол | `diagnostic_reports.pg_request_id`, `pg_diagnosis_id` |
| **История заявки** | `status_history`: единственный источник истины по статусам | Лента событий. События `status_changed` являются **проекцией** из PostgreSQL | `request_events.pg_status_history_id` |

Копия `name` и `article` в `parts_catalog.pg_snapshot` нужна только для поиска по каталогу. Она обновляется из PostgreSQL, при расхождении побеждает PostgreSQL.

## 5. Правила согласованности

1. **Нет внешних ключей между СУБД.** Ссылки хранятся как `pg_*` (int64). Приложение проверяет существование записи при вставке, а периодическая сверка находит «сирот».
2. **Порядок записи: сначала PostgreSQL, затем MongoDB.** Проекции из PostgreSQL идемпотентны (уникальный `pg_status_history_id` и `upsert`), поэтому повторная доставка событий безопасна.
3. **Деньги, остатки и статусы не хранятся в MongoDB.** В `equipment_models` есть только справочный диапазон `typical_cost_range`. Это ориентир, а не счёт и не смета.
4. **Копии данных из PostgreSQL лежат в отдельном подобъекте** `pg_snapshot` с отметкой `synced_at`.
5. **Недоступность MongoDB не останавливает бизнес-процесс.** Приём, ремонт, резервирование и оплата работают без неё. Протоколы и события ставятся в очередь на повторную запись.
6. **Персональные данные клиента в MongoDB не хранятся**: ни ФИО, ни телефон, ни email. В событиях есть только `pg_employee_id` автора. RLS PostgreSQL на MongoDB не распространяется, поэтому доступ ограничивается ролями MongoDB (запись только у сервиса, чтение у отчётов). Свободный текст в комментариях тоже не должен содержать ПДн.
7. **Восстановление из бэкапа.** Бэкапы делаются независимо. После восстановления PostgreSQL проекции `status_changed` пересобираются из `status_history`.

## 6. Пример сверки ссылок (раз в сутки)

```javascript
// MongoDB: какие заявки упоминаются в ленте
db.request_events.distinct("pg_request_id")
```

```sql
-- PostgreSQL: найти идентификаторы, которых больше нет (передать массив из шага выше)
SELECT x.id
FROM unnest($1::bigint[]) AS x(id)
LEFT JOIN request r ON r.id = x.id
WHERE r.id IS NULL;
```

# Задачи, для которых документная модель имеет преимущество

## Критерии выбора

Задача переезжает в MongoDB, если выполняется хотя бы три из пяти условий:

1. Структура данных **различается** между экземплярами (разные типы техники, разные чек-листы).
2. Данные читаются и пишутся **как единое целое** (один протокол, одна карточка).
3. В реляционной модели потребовалось бы **три и более таблиц** и `JOIN` ради одного логического объекта.
4. Данные образуют **append-only поток** разнородных записей.
5. Нет **межстрочных инвариантов** (уникальность по условию, балансы, блокировки).

## Задача 1. Справочник моделей техники с разными характеристиками

**Проблема в PostgreSQL.** У смартфона есть ёмкость батареи и класс влагозащиты, у ноутбука процессор и тип накопителя, у принтера технология печати и скорость. Варианты в реляционной модели:

- разреженная таблица, где большинство столбцов `NULL`;
- схема EAV («сущность-атрибут-значение») с `JOIN` на каждый атрибут;
- один столбец `JSONB`, то есть, по сути, документ внутри реляционной таблицы.

**Решение в MongoDB.** Коллекция `equipment_models`. Поле `specs` — произвольный вложенный документ, обязательный каркас проверяется валидатором (`type`, `manufacturer`, `model`, `model_key`). Типовые неисправности вложены массивом `common_faults`, потому что без модели они не существуют и читаются вместе с ней.

**Выигрыш.** Новый тип техники («Планшет», «Монитор») добавляется без миграции. Карточка модели читается одним запросом.

## Задача 2. Протокол диагностики

**Проблема в PostgreSQL.** Таблица `diagnosis` хранит только `result` и `detected_malfunction`. Подробный протокол (чек-лист из 5–30 пунктов, показания приборов, найденные неисправности с рекомендованными запчастями, фото) потребовал бы четырёх таблиц: отчёт, пункты, неисправности, вложения. Набор пунктов зависит от типа техники.

**Решение в MongoDB.** Коллекция `diagnostic_reports`. Один документ содержит `checks[]`, `found_faults[]` и `attachments[]`. Повторная диагностика после ремонта — новый документ с `revision` + 1 и `kind: "recheck"`.

**Выигрыш.**

- Один протокол читается и печатается одним запросом, без `JOIN`.
- Обновление документа атомарно.
- Аналитика по вложенным пунктам делается через `$elemMatch`, например «все ноутбуки с провалом проверки температуры в простое».

`diagnosis` в PostgreSQL сохраняется как юридически значимый краткий итог. Протокол в MongoDB его **детализирует**, но не заменяет.

## Задача 3. Лента событий заявки

**Проблема в PostgreSQL.** `status_history` имеет жёсткую схему (`old_status`, `new_status`, `reason`) и отлично подходит для аудита статусов. Но звонки клиенту, комментарии мастера, фото, подтверждения и уведомления имеют **разные наборы полей**, и их число растёт быстрее всего остального.

**Решение в MongoDB.** Коллекция `request_events`. Общий каркас (`pg_request_id`, `type`, `created_at`, `author`) и `payload`, структура которого зависит от `type`. Для `status_changed` валидатор требует `payload.old_status`, `payload.new_status` и `pg_status_history_id`.

**Выигрыш.**

- Новый тип события не требует миграции.
- Лента пагинируется по индексу `(pg_request_id, created_at)`.
- Старые события легко архивировать или удалять по TTL.
- Запись события не конкурирует за блокировки с транзакциями PostgreSQL.

## Задача 4. Каталог запчастей: атрибуты и совместимость

**Проблема в PostgreSQL.** Атрибуты зависят от категории: у батареи есть ёмкость и напряжение, у термопасты теплопроводность и объём. Совместимость запчастей с моделями — связь M:N, которая в реляционной модели требует отдельной таблицы.

**Решение в MongoDB.** Коллекция `parts_catalog`. Атрибуты лежат в `attributes`, совместимость в массиве `compatible_model_ids` с multikey-индексом.

**Выигрыш.** Вопрос «что подходит к модели X» превращается в один запрос по индексу. Цена и остаток остаются в `part` (PostgreSQL), потому что именно там работают резервирование и триггер проверки остатка.

## Что намеренно остаётся в PostgreSQL

| Данные | Почему не MongoDB |
|---|---|
| Резервирование запчастей | Нужны `FOR UPDATE` и триггер: два мастера не должны занять один остаток |
| Оплата | Деньги требуют ACID и `CHECK`-ограничений |
| Статус заявки | Допустимые переходы и зависимые поля (`waiting_reason`, `approval_at`) охраняются ограничениями |
| Назначение мастера | Частичный уникальный индекс «один активный» |
| Клиенты и сотрудники | ПДн, RLS, роли |
