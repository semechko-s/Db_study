# Приведение логической модели к третьей нормальной форме

## 1. Цель нормализации

На этапе нормализации логическая модель PostgreSQL была проверена на соответствие первой, второй и третьей нормальным формам. Целью нормализации является устранение избыточности данных, предотвращение аномалий вставки, изменения и удаления, а также обеспечение согласованности данных.

В качестве основы использована логическая модель PostgreSQL системы сервисного центра, построенная на основе ранее разработанной концептуальной ER-модели.

В модели используются суррогатные идентификаторы `id` в качестве первичных ключей таблиц. Связи между сущностями реализуются с помощью внешних ключей.

## 2. Проверка первой нормальной формы

Модель соответствует требованиям **первой нормальной формы (1НФ)**.

Каждая таблица содержит атомарные атрибуты: одно поле хранит одно значение, отсутствуют повторяющиеся группы атрибутов и массивы значений.

Например, таблица `client` содержит отдельные атрибуты:

- `id`;
- `full_name`;
- `phone`;
- `email`.

Таблица `equipment` также содержит отдельные атомарные характеристики оборудования:

- `id`;
- `client_id`;
- `type`;
- `manufacturer`;
- `model`;
- `serial_number`;
- `condition_description`;
- `status`.

Аналогичный принцип применяется к остальным таблицам модели.

**Вывод:** все атрибуты представлены в атомарном виде, поэтому модель соответствует 1НФ.

## 3. Проверка второй нормальной формы

**Вторая нормальная форма (2НФ)** требует, чтобы таблица уже находилась в 1НФ и каждый неключевой атрибут полностью зависел от первичного ключа.

В итоговой модели в качестве первичных ключей используются отдельные атрибуты `id`. Поэтому частичные зависимости неключевых атрибутов от части составного ключа отсутствуют.

Отдельно была рассмотрена таблица `employee`. В исходном варианте атрибут `specialization` ошибочно был включён в состав первичного ключа вместе с `id`. Поскольку сотрудник однозначно определяется своим идентификатором, `specialization` не должна являться частью первичного ключа.

После исправления таблица имеет структуру:

```
employee
-------------------------
id             PK
full_name
specialization
phone
email
```

Теперь все неключевые атрибуты сотрудника зависят от `employee.id`:

```
employee.id → full_name
employee.id → specialization
employee.id → phone
employee.id → email
```

Таким образом, частичных зависимостей нет, и таблица соответствует 2НФ.

**Вывод:** после исключения `specialization` из первичного ключа таблицы модели соответствуют требованиям 2НФ.

# 4. Проверка третьей нормальной формы

**Третья нормальная форма (3НФ)** требует отсутствия транзитивных зависимостей неключевых атрибутов от первичного ключа.

При проверке модели была обнаружена транзитивная зависимость в таблице `request`.

В таблице `equipment` хранится информация о владельце оборудования:

```
equipment
-------------------------
id
client_id
...
```

Таким образом:

```
equipment.id → client_id
```

При этом заявка связана с конкретным оборудованием:

```
request.id → equipment_id
```

Следовательно, если одновременно хранить `client_id` в `request`, возникает зависимость:

```
request.id → equipment_id → client_id
```

То есть `client_id` в таблице `request` определяется не непосредственно заявкой, а через связанное с ней оборудование. Это является транзитивной зависимостью и нарушает требования 3НФ.

---

## 5. Устранение транзитивной зависимости

Для устранения избыточности атрибут `client_id` был удалён из таблицы `request`.

Итоговая структура заявки содержит связь с оборудованием:

```
request
-------------------------
id             PK
equipment_id   FK
operator_id    FK
created_at
received_at
description
status
waiting_reason
preliminary_cost
total_cost
client_approved
approval_at
issued_at
completed_at
```

Информация о клиенте теперь получается через связанное оборудование:

```
request
   ↓
equipment
   ↓
client
```

То есть:

```
request.equipment_id
        ↓
equipment.client_id
        ↓
client.id
```

Таким образом, информация о владельце оборудования хранится только в одном месте — в таблице `equipment`.

Это позволяет избежать ситуации, когда в `request.client_id` и `equipment.client_id` находятся разные значения для одного оборудования.

**Вывод:** удаление `client_id` из `request` устраняет транзитивную зависимость и приводит таблицу к 3НФ.

---

# 6. Дополнительные изменения для соответствия связям модели

В процессе проверки также были скорректированы ограничения, чтобы физическая структура PostgreSQL соответствовала кардинальностям концептуальной модели.

### Таблица `work`

В исходной версии для `work.request_id` было установлено ограничение `UNIQUE`.

Это означало бы, что для одной заявки можно создать только одну запись `work`.

Однако концептуальная модель предусматривает связь:

```
Заявка 1 : N Работа
```

и в предметной области в рамках одной заявки может выполняться несколько работ. Поэтому ограничение `UNIQUE`с `work.request_id` было удалено.

Теперь несколько работ могут ссылаться на одну заявку:

```
request 1 ───── N work
```

Это изменение не связано непосредственно с 3НФ, но необходимо для соответствия логической модели установленным кардинальностям.

---

### Таблица `payment`

Для `payment.request_id` было добавлено ограничение `UNIQUE`.

Концептуальная модель предусматривает:

```
Заявка 1 : 1 Оплата
```

Поэтому одна заявка должна иметь не более одной записи оплаты.

Ограничение:

```
payment.request_id UNIQUE
```

обеспечивает это требование на уровне базы данных.

В результате проверки и нормализации логической модели были устранены частичная зависимость в таблице `employee` и транзитивная зависимость в таблице `request`. Дополнительно ограничения уникальности были скорректированы в соответствии с кардинальностями связей предметной области. # 8. Решение по намеренной денормализации

В рамках разработки логической модели было принято решение **не применять намеренную денормализацию**.

Все данные хранятся в таблицах, соответствующих их предметной области, а повторное хранение одних и тех же данных не требуется. В частности, информация о клиенте не дублируется в таблице `request`: клиент определяется через оборудование, связанное с заявкой.

Хранение `client_id` одновременно в таблицах `equipment` и `request` привело бы к дублированию данных и могло бы вызвать нарушение согласованности. Например, при изменении владельца оборудования потребовалось бы дополнительно изменять связанные заявки.

 Поэтому команда решила сохранить нормализованную структуру в 3НФ и не вводить намеренную денормализацию. Возможные проблемы производительности предполагается решать средствами PostgreSQL, в частности с помощью индексов и оптимизации запросов, а не дублированием данных.

### Вывод по денормализации

**Намеренная денормализация в текущей версии модели отсутствует.** Модель сохраняется в нормализованном виде, поскольку имеющиеся бизнес-сценарии не требуют дублирования данных для повышения производительности.
