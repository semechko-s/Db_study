## 6. Проверка масштабов генерации

### Режим development

Для проверки режима разработки создана отдельная чистая база данных `service_center_generator_dev`. После применения миграций выполнена команда:

**Результат:** требование от 50 000 до 100 000 строк в крупнейшей таблице выполнено.

### Режим load

Для проверки нагрузочного режима создана отдельная чистая база данных `service_center_generator_load`. После применения миграций выполнена команда:

`python3 scripts/generate_data.py --mode load --seed 45 --batch-size 1000`

Генерация завершилась успешно, транзакция зафиксирована. В таблицу `notification` добавлено 3 000 000 записей. Контрольный запрос `SELECT COUNT(*) FROM notification` подтвердил наличие ровно 3 000 000 строк.

**Результат:** требование не менее 3 000 000 строк в крупнейшей таблице выполнено.

### Итог

Оба режима генерации протестированы на отдельных чистых базах данных. Фактические размеры крупнейшей таблицы подтверждены запросами к PostgreSQL. Оба требования к масштабам генерации выполнены.

## 7. Проверка воспроизводимости генерации

Для проверки воспроизводимости генератора были созданы две независимые чистые базы данных PostgreSQL: `service_center_generator_check` и `service_center_generator_check2`. В обе базы данных были применены одинаковые миграции, после чего генератор был запущен с одинаковыми параметрами.

Команды запуска:

```bash
PGDATABASE=service_center_generator_check python3 scripts/generate_data.py --mode development --seed 42
```

```bash
PGDATABASE=service_center_generator_check2 python3 scripts/generate_data.py --mode development --seed 42
```

В обеих базах данных генерация завершилась успешно, транзакции были зафиксированы.

Для проверки идентичности результатов были вычислены контрольные суммы содержимого таблиц. Перед сравнением строки каждой таблицы упорядочивались, а в контрольную сумму включались значения всех столбцов записей.

Результаты сравнения показали, что контрольные суммы совпали во всех 14 таблицах:

- `equipment`;
- `part`;

- `diagnosis`;
- `work`;
- `repair`;
- `part_reservation`;
- `used_part`;
- `payment`;

Таким образом, при одинаковой начальной конфигурации базы данных, одинаковых миграциях, режиме генерации и значении `seed` генератор создаёт идентичный набор данных.

**Вывод:** воспроизводимость генерации подтверждена для режима `development` при значении `seed = 42`. Использование фиксированного начального значения генератора псевдослучайных чисел позволяет повторять тестовые сценарии и получать одинаковые результаты при соблюдении одинаковых исходных условий.

## 8. Проверка распределения данных

Для проверки разнообразия и реалистичности тестовых данных были проанализированы распределения статусов заявок, типов оборудования и дат создания заявок в режиме `load`.

**Распределение статусов заявок.** В таблице `request` представлены все восемь предусмотренных статусов. Наиболее распространённый статус — «В ремонте» (181 запись, 18,1%), наименее распространённый — «Отменена» (43 записи, 4,3%). Распределение не является равномерным.

**Распределение типов оборудования.** В таблице `equipment` представлены все восемь типов оборудования. Наиболее распространённый тип — «Ноутбук» (79 записей, 26,33%), наименее распространённый — «Принтер» (16 записей, 5,33%). Это подтверждает наличие неодинаковой частоты встречаемости значений.

**Распределение дат.** Даты создания заявок охватывают период с 10 октября 2024 года по 8 октября 2026 года. В выборке представлены 533 различных календарных дня.

**Вывод:** тестовые данные содержат разнообразные статусы и типы оборудования, неравномерные распределения категориальных значений и даты, охватывающие продолжительный период. Это позволяет использовать набор данных для проверки запросов и анализа поведения базы данных на различных значениях.

## 9. Проверки целостности

Для проверки корректности сгенерированных данных были выполнены проверки бизнес-ограничений в режимах `development` и `load`.

Проверялись следующие условия:

- отсутствие причин ожидания у заявок со статусом «Ожидание»;
- соответствие признака согласования клиента наличию даты согласования;
- отсутствие даты приёма оборудования, предшествующей дате создания заявки;
- наличие даты выдачи у закрытых заявок;
- отсутствие отрицательной стоимости заявок, работ, ремонтов и платежей;
- отсутствие даты окончания работы или ремонта, предшествующей дате начала;
- наличие результата у завершённых ремонтов;
- соответствие статуса платежа наличию даты оплаты;
- соответствие суммы платежа его статусу.

Все 13 выполненных проверок в каждой из двух тестовых баз завершились с результатом `0` нарушений.

Дополнительно проверена схема PostgreSQL: все 66 ограничений были валидированы, непроверенных ограничений не осталось.

**Вывод:** сгенерированные данные прошли выполненные проверки бизнес-правил и ограничений базы данных.
