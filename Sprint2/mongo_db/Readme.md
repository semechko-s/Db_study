# Sprint 5. Документная модель MongoDB

## 1. Цель работы

Цель работы — разработать документную модель базы данных
для сервисного центра с использованием MongoDB и языка Go.

В качестве предметной области используется система
учёта клиентов, заявок на ремонт и запчастей.

## 2. Коллекции

В базе данных `service_center` созданы три коллекции:

### clients

Содержит информацию о клиентах:

- `_id` — идентификатор клиента;
- `name` — имя клиента (обязательное поле);
- `phone` — телефон;
- `email` — электронная почта;
- `created_at` — дата создания документа.

При создании клиента необходимо указать имя и хотя бы один
контактный способ: телефон или электронную почту.

### service_requests

Содержит информацию о заявках на ремонт:

- `_id` — идентификатор заявки;
- `client_id` — ссылка на клиента из коллекции `clients`;
- `equipment` — информация об оборудовании;
- `description` — описание неисправности;
- `status` — статус заявки;
- `waiting_reason` — причина ожидания, если заявка находится в статусе «Ожидание»;
- `client_approved` — признак согласия клиента на ремонт;
- `parts` — массив использованных или запланированных запчастей;
- `repair` — информация о ремонте;
- `created_at` — дата создания заявки;
- `updated_at` — дата последнего изменения заявки.

### parts

Содержит информацию о запчастях:

- `_id` — идентификатор запчасти;
- `name` — название;
- `price` — цена;
- `stock` — количество на складе.

Цена и остаток не могут быть отрицательными.

## 3. Связь один ко многим (1:N)

Один клиент может иметь несколько заявок на ремонт.

Для реализации связи используется поле `client_id`
в коллекции `service_requests`.

Идентификатор клиента ссылается на документ
в коллекции `clients`.

Таким образом, один клиент может быть связан
с несколькими заявками. Перед созданием заявки программа
проверяет, что указанный клиент существует.

## 4. Связь многие ко многим (M:N)

Одна заявка может содержать несколько запчастей.
Одна и та же запчасть может использоваться
в разных заявках.

Для реализации связи используется массив `parts`
внутри документа заявки.

В массиве хранятся:

- `part_id` — ссылка на запчасть;
- `quantity` — количество использованных запчастей.

Сами запчасти находятся отдельно в коллекции `parts`.
Программа проверяет существование каждой указанной запчасти,
положительность количества и отсутствие повторов одной запчасти
в пределах одной заявки.

## 5. Embedding

Embedding используется для хранения информации
об оборудовании непосредственно внутри заявки.

Например:

```json
{
    "equipment": {
        "type": "Смартфон",
        "manufacturer": "Samsung",
        "model": "Galaxy S22",
        "serial_number": "SN-001"
    }
}
```

Такое решение выбрано потому, что информация
об оборудовании обычно читается вместе с заявкой.

Это позволяет получить данные одним запросом.

Также информация об оборудовании относится к конкретной заявке
и не требует частого независимого обновления.

Размер вложенного документа небольшой,
поэтому embedding является удобным решением.

## 6. Referencing

Referencing используется для связи заявок с клиентами
и запчастями.

В заявке хранится `client_id`,
а в массиве `parts` — `part_id`.

Сами документы клиентов и запчастей хранятся
в отдельных коллекциях.

Такое решение выбрано потому, что один клиент
может иметь много заявок, а одна запчасть
может использоваться в разных заявках.

Если информация о клиенте или запчасти изменится,
достаточно обновить один документ.

Это позволяет избежать дублирования данных
и чрезмерного увеличения размера документов.

Для получения информации из связанных коллекций
можно использовать оператор `$lookup`.

## 7. CRUD и валидация данных

В программе на Go реализованы операции добавления,
чтения, обновления и удаления документов (CRUD)
для коллекций `clients`, `service_requests` и `parts`.

Для проверки структуры документов используется JSON Schema validation
на стороне MongoDB. Проверяются типы данных, обязательные поля,
допустимые значения статусов, а также неотрицательные цена и остаток.

Дополнительно в приложении реализованы бизнес-правила:

1. Клиент, указанный в заявке, должен существовать.
2. Для статусов «В ремонте», «Готова» и «Закрыта» требуется согласие клиента.
3. Для статуса «Ожидание» необходимо указать причину ожидания.
4. Все запчасти из заявки должны существовать, а их количество должно быть положительным.

Удаление клиента запрещено, если на него ссылаются заявки.
Удаление запчасти запрещено, если она используется в заявках.

## 8. Запуск программы

Для запуска необходимо:

1. Установить Go.
2. Установить и запустить MongoDB.
3. Открыть папку проекта `Sprint2/mongo_db`.
4. Выполнить команды:

```bash
go mod tidy
go run .
```

MongoDB должна быть доступна по адресу:

`mongodb://localhost:27017`

Другой адрес подключения можно указать через переменную окружения
`MONGODB_URI`.

Для демонстрации CRUD необходимо выполнить:

```bash
go run . demo
```

Демонстрация создаёт временные документы, выполняет операции
добавления, чтения, обновления и удаления, после чего удаляет
только созданные ею данные. Существующие документы и коллекции
не очищаются.

## 9. Вывод

В ходе работы была разработана документная модель
для сервисного центра.

Созданы три коллекции: `clients`, `service_requests` и `parts`.

Реализованы связи 1:N и M:N.

Использованы два подхода к хранению данных:
embedding и referencing.

Также реализованы CRUD-операции, проверка структуры документов
с помощью JSON Schema validation и дополнительные бизнес-правила
с использованием языка Go.
