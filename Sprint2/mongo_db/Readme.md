# Документная модель MongoDB

В базе `service_center` используются четыре коллекции из [README спринта](../README.md#распределение-данных-между-postgresql-и-mongodb).

| Коллекция | Данные |
|---|---|
| `equipment_models` | Модели техники, их характеристики и типовые неисправности |
| `parts_catalog` | Атрибуты деталей и ссылки на совместимые модели |
| `diagnostic_reports` | Подробные протоколы диагностики со списками проверок |
| `request_events` | События заявки с датой, автором и деталями события |

## Связи и способ хранения

- **1:N.** У одной заявки может быть несколько протоколов диагностики. Каждый протокол содержит `pg_request_id` заявки из PostgreSQL и свой номер `revision`.
- **M:N.** Одна деталь подходит к нескольким моделям, а одной модели подходят несколько деталей. В массиве `compatible_model_ids` хранятся идентификаторы моделей из `equipment_models`.
- **Встраивание.** Массив `checks` хранится внутри протокола. Проверки читают и записывают вместе с протоколом, а при повторной диагностике создают новую ревизию. Чек-лист обычно состоит из 5–30 коротких записей, поэтому мало увеличивает размер документа.
- **Ссылка.** По идентификатору модели можно найти совместимые детали одним запросом. Характеристики модели читаются по необходимости и обновляются в одном документе. Идентификаторы занимают меньше места, чем копии карточек моделей в каждой детали.

## Запуск

Запусти MongoDB и выполни из этой папки:

```bash
go run .       # создаёт коллекции и индексы
go run . demo  # показывает связи на примере
```

По умолчанию программа подключается к `mongodb://localhost:27017`. Другой адрес можно задать через `MONGODB_URI`. Демонстрация создаёт временную базу и удаляет её после запуска. Идентификаторы PostgreSQL в примере условные.

Замеры двух запросов и объяснение составных индексов приведены в [отчёте по оптимизации](PERFORMANCE.md). Повторить эксперимент можно командой `go run . benchmark`.

## Replica Set и проверка переключения primary

В [Compose-стенде](../infra/mongo-replication/compose.yaml) три голосующих узла с данными в наборе `rs0`. Каждый хранит свою копию в отдельном Docker volume. Primary принимает записи и заносит операции в oplog, а secondary применяют операции из этого журнала. Для выборов нужно большинство голосов — два из трёх. После остановки primary оставшиеся узлы могут выбрать новый primary и подтверждать запись большинством. [Выборы в MongoDB](https://www.mongodb.com/docs/manual/core/replica-set-elections/)

Стенд рассчитан на локальный Docker Engine под Linux. Узлы делят сетевое пространство хоста и слушают только `localhost` на портах 27117–27119. Эти же адреса MongoDB сообщает драйверу, поэтому он может найти новый primary напрямую с хоста.

Команды для прогона:

```bash
rs=../infra/mongo-replication/replica-set.sh
"$rs" up
export MONGODB_URI="$("$rs" uri)"
go run . demo
"$rs" failover
"$rs" status
```

Команда `up` запускает контейнеры, инициализирует набор при первом запуске и ждёт один `PRIMARY` и два `SECONDARY`. `go run . demo` запускает существующий сценарий сервисного центра через тот же адрес подключения. Скрипт переключения сам находит текущий primary, пишет контрольный документ в `service_center.replica_set_probe` и останавливает контейнер с primary. После выборов скрипт проверяет, что адрес primary изменился, читает прежний документ и проверяет запись и чтение нового. Контрольные документы остаются в базе с идентификатором запуска в выводе. В конце скрипт запускает остановленный контейнер и проверяет, что прежний primary вернулся как `SECONDARY`.

Успешный запуск покажет смену адреса primary, увеличение `term` в `rs.status()`, строки `WRITE before: OK`, `READ before: OK` и `WRITE + READ after: OK`. Финальный статус снова содержит один `PRIMARY` и два `SECONDARY` с `health: 1`. Скрипт измеряет время от вызова команды остановки до обнаружения нового primary, включая работу Docker и опрос. Остановить стенд с сохранением данных можно командой `docker compose -f ../infra/mongo-replication/compose.yaml stop`.

При проверке primary сменился с `localhost:27118` на `localhost:27117` за 11 секунд, `term` вырос с 2 до 3. Во время чтения прежнего документа и записи нового остановленный узел был недоступен (`health: 0`).

### Настройки клиента для проекта

Настройки зафиксированы в URI, который печатает `replica-set.sh uri`. Его используют проверка переключения и Go-модуль через `MONGODB_URI`.

| Настройка | Значение | Влияние на сервисный центр |
|---|---|---|
| Read concern | `majority` | Чтение протоколов диагностики и событий заявки идёт по снимку, подтверждённому большинством. Это исключает отображение операций, которые могут откатиться при обычном переключении primary. Снимок может отставать от самых свежих записей. [Read concern](https://www.mongodb.com/docs/manual/reference/read-concern-majority/) |
| Write concern | `w=majority`, `wtimeoutMS=5000` | Успех записи означает подтверждение от двух узлов с данными. Репликация добавляет задержку. Если за пять секунд подтверждение не пришло, результат записи может быть неизвестен клиенту. Для повторной доставки проекции статуса используется тот же `pg_status_history_id` и идемпотентный upsert. [Write concern](https://www.mongodb.com/docs/manual/reference/write-concern/) |
| Read preference | `primary` | Протоколы и лента читаются с primary, поэтому обычное отставание secondary не влияет на выбор узла для этих запросов. Во время выборов чтения и записи могут ждать выбора узла или завершиться ошибкой. Остальные бизнес-операции сервисного центра опираются на PostgreSQL. [Read preference](https://www.mongodb.com/docs/manual/core/read-preference/) |
