# Версионирование MongoDB: diagnostic_reports

## Задача и форматы

`revision` — номер повторной диагностики, **не** версия структуры документа. Для версии схемы используется отдельное поле `schema_version`.

- **v1**: `schema_version` отсутствует или равно 1; элементы `checks` имеют `{ "name": "power", "passed": true }`.
- **v2**: `schema_version: 2`, `report_format: "diagnostic.v2"`; элементы `checks` имеют `{ "name": "power", "status": "pass" }`.
- Преобразование: `passed: true` → `status: "pass"`; `passed: false` → `status: "fail"`. Значение `"skipped"` разрешено в новых v2-документах, но **не может быть восстановлено из v1**, потому что исходный boolean его не содержал.
- Поле `passed` после миграции удаляется. Другие поля, включая `_id`, `revision`, PostgreSQL-идентификаторы, вложенные расширения и списки неисправностей, сохраняются.

## План безопасного внедрения

1. Сначала подготовить приложение к чтению **обеих версий** и записи v2. Нынешний `Sprint2/mongo_db/main.go` команды пока умеет работать только с v1.
2. Согласовать с командой JSON Schema валидатор: сейчас `ensureValidators` требует `checks[].passed`, а v2 использует `checks[].status`. Запуск обычного приложения может заново установить старый валидатор. **Два файла этой задачи не меняют чужой код и не обеспечивают полной совместимости приложения с v2.**
3. Проверить миграцию на отдельной тестовой базе `migration_test_*`, затем отдельно согласовать процедуру для рабочей базы. Включить резервное копирование и остановить конкурирующие записи на время перехода.
4. Только после проверки и согласования переключать реальные данные на v2.

## Утилита миграции

Файл `migration/main.go` — самостоятельная команда, использующая уже имеющийся MongoDB Go driver из `go.mod` проекта. Из папки `Sprint2/mongo_db`:

```sh
go run ./migration/main.go status --db migration_test_manual
go run ./migration/main.go up --db migration_test_manual
go run ./migration/main.go down --db migration_test_manual
```

MongoDB URI задаётся переменной `MONGODB_URI` или `--uri`. Команды намеренно **разрешены только для баз с именем `migration_test_*`**: это защита от случайного изменения командной базы `service_center`. Утилита не создаёт тестовые данные: тестовую базу нужно заполнить отдельно. Запуск `up` при пустой базе не доказывает корректность преобразования.

`up` проверяет все отчёты до изменений, сохраняет исходные и целевые BSON-документы в `diagnostic_reports_v1_v2_backup`, затем заменяет v1 на v2. Повторный запуск пропускает уже преобразованные v2. При несовпадении резервной копии, неподдерживаемой версии или конкурентном изменении команда останавливается. Запись v2 использует `bypassDocumentValidation` только при переходе вверх, потому что старый валидатор требует `passed`; это требует соответствующих прав MongoDB и **не изменяет валидатор**. При down обход валидации отключён: восстановленный v1 должен пройти действующий валидатор. Остальные поля сохраняются.

`down` откатывает **только** документы с сохранёнными резервными копиями, если их содержимое не изменялось после `up`. Новые документы v2 не трогает. При конфликте откат останавливается, резервные копии остаются. При прерывании операции возможен частичный результат: следует проверить `status`, исследовать конфликт и повторить команду. Операции не являются одной общей транзакцией. Бэкапы не удаляются автоматически.

## Ограничения

- Нельзя запускать на реальных данных без отдельного согласования и подготовки приложения/валидатора. Текущий Go-код команды создаёт v1 и может не принимать v2 при обновлении.
- `status` проверяет формат и считает v1/v2, но не подтверждает готовность основного приложения.
- Проверено на отдельном локальном сервере MongoDB 7.0.45 и Go 1.23.12. Для другой версии сервера нужна повторная проверка; используется `$getField` (MongoDB 5.0+).
- Если `down` встречает `status: "skipped"` в изменённом после миграции документе, он не пытается угадывать прежний boolean и отказывается от небезопасного отката.


## Защита данных и повторный запуск

Перед первым изменением проверяются все документы. Дублирующиеся BSON-ключи,
неизвестные версии, смешанные passed/status и неправильные типы блокируют
миграцию. Сравнение перед заменой использует simple collation и рекурсивную
проверку BSON-типов, чтобы не потерять изменения регистра или int/long/double.
Тем не менее на время прохода нужно остановить writers: общего снимка и
транзакции на коллекцию нет. Новые вставки могут потребовать повторного up.
Откат требует точного совпадения BSON с сохранённым after; изменения порядка
полей тоже считаются конфликтом. Удалённые документы не восстанавливаются.
Нельзя повторно использовать `_id` удалённых документов между up/down.

Бэкап хранится в той же базе и не заменяет независимую резервную копию.
Не меняйте его вручную; ограничьте права записи оператором. Записи подтверждаются
с write concern majority. После сбоя между insert backup и replace повторный
up использует ту же копию. После успешного down возможен новый up, только если
оригинал не менялся. При несовпадении старой копии программа останавливается,
не затирая историю. Это относится и к копиям предыдущего аддитивного варианта
миграции из локального коммита d98489be: новый формат after отличается; такие
копии нельзя переиспользовать молча. Для тестирования используйте свежую базу.

Все документы и план загружаются в память. Для больших коллекций нужна
пакетная обработка. Оболочка before/after может превысить лимит BSON 16 MB:
тогда соответствующая резервная запись не создастся и документ не изменится,
но предыдущие документы прохода уже могут быть преобразованы. Общий таймаут
CLI — 2 минуты. При ошибках процесс возвращает ненулевой код.
Именование migration_test_* не проверяет, что URI указывает на тестовый сервер:
никогда не передавайте URI общей или рабочей MongoDB.

## Фактическая проверка двухфайлового варианта

Проверка 2026-11-09 выполнена в отдельной распакованной копии проекта.
Исходная рабочая ветка и файлы команды не изменялись. Временные проверочные
сценарии не входят в поставку: ZIP содержит только VERSIONING.md и migration/main.go.

Успешно выполнены:

- компиляция самостоятельной программы migration/main.go и `go build ./...`;
- `go vet ./...`;
- временные race-тесты: оба boolean-преобразования, сохранение расширений,
  исходный и целевой BSON в backup, точный roundtrip для legacy и явного v1,
  повторные up/down, native v2 со skipped без резервной копии;
- отказ при последующей правке, неизвестной версии, дублирующихся ключах,
  конфликте старой копии и конкурентной смене регистра при нечувствительной
  collation; восстановление после прерывания между backup и replace;
- CLI status/up/up/status/down/down под настоящим валидатором из main.go;
- отказ down при валидаторе, запрещающем v1 (без обхода валидации);
- отдельная проверка настоящих Create/Read/Update и ensureValidators: Read
  возвращает v2 как BSON, но Create и Update с реальными изменениями отклоняются
  старым серверным валидатором. No-op Update может не вызывать валидацию;
- исходная демонстрация `go run . demo`.

**Ограничение текущей локальной ветки sprint5:** в d98489be дополнительно есть
migration/demo.go, migration/main_test.go и workflow mongodb-migration.yml от
предыдущего варианта. С новым форматом полный `go test ./...` при подключённой
MongoDB падает в прежнем TestIntegration: demo пытается вставить v2 без passed
под валидатором v1 без bypass. Workflow также вызывает `go run ./migration demo`,
но этот двухфайловый вариант поддерживает только status/up/down. Изменение этих
трёх файлов выходит за разрешённые два файла; они оставлены нетронутыми.
Следовательно, проход полного прежнего CI не заявляется. Для интеграции именно
в эту локальную ветку потребуется отдельное согласование обновления её тестов,
демонстрации и workflow. Ослаблять валидатор или менять формат ради старых
тестов небезопасно. Коммит и push в ходе этой проверки не выполнялись.
