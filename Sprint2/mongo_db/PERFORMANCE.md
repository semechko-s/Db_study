# Оптимизация запросов MongoDB

Для эксперимента выбраны два сценария сервисного центра. Оба возвращают полные документы и сортируют все совпадения.

1. **История действий сотрудника.** Найти события сотрудника 42 и показать свежие первыми. Исходный индекс `{pg_request_id: 1, created_at: -1}` обслуживает историю отдельной заявки. Здесь фильтр задан по сотруднику, поэтому исходный индекс не даёт подходящего диапазона поиска.
2. **История ревизий диагностики.** Найти протоколы диагностики 42 и показать поздние ревизии первыми. Исходный уникальный индекс `{pg_request_id: 1, revision: 1}` задаёт уникальность ревизии внутри заявки. Для поиска по `pg_diagnosis_id` нужен другой первый ключ.

## Запросы и индексы

Эквивалент запросов бенчмарка в `mongosh`:

```javascript
db.request_events
  .find({ "author.pg_employee_id": NumberLong("42") })
  .sort({ created_at: -1 })
  .explain("executionStats");

db.diagnostic_reports
  .find({ pg_diagnosis_id: NumberLong("42") })
  .sort({ revision: -1 })
  .explain("executionStats");
```

После первого замера бенчмарк создаёт следующие индексы и повторяет те же запросы:

```javascript
db.request_events.createIndex({ "author.pg_employee_id": 1, created_at: -1 });
db.diagnostic_reports.createIndex({ pg_diagnosis_id: 1, revision: -1 });
```

Первое поле каждого индекса соответствует условию равенства. MongoDB переходит к диапазону ключей выбранного сотрудника или диагностики. Внутри диапазона записи уже упорядочены по второму полю, поэтому отдельная сортировка не нужна. При записи MongoDB также поддерживает новые индексы, а на диске они занимают дополнительное место. [Документация по составным индексам](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-compound/)

## Воспроизведение

Запустить MongoDB и выполнить из каталога `Sprint2/mongo_db`:

```bash
go run . benchmark > /tmp/mongo-explain.json
```

По умолчанию используется `mongodb://localhost:27017`. Для другого адреса задай `MONGODB_URI`. Бенчмарк создаёт уникальную временную базу, устанавливает исходные индексы и валидаторы, вставляет по 120 000 синтетических документов в каждую из двух коллекций и удаляет временную базу в конце. Обычный запуск `go run .` создаёт в `service_center` как исходные, так и два новых индекса.

Для каждого запроса на каждом этапе выполняется один прогрев и пять замеров. Данные, фильтр и сортировка одинаковы до и после. Оптимизатор выбирает план сам, без `hint()`. `explain("executionStats")` выполняет выигравший план и возвращает дерево плана в `queryPlanner.winningPlan` и метрики в `executionStats`. [Документация по explain](https://www.mongodb.com/docs/manual/reference/explain-results/)

## Результаты на MongoDB 7.0.48

Все 20 ответов сервера, включая полные деревья планов, сохранены в [performance_explain.json](performance_explain.json). В таблице указана медиана времени пяти прогонов. Остальные счётчики совпали во всех пяти прогонах соответствующего этапа.

| Запрос | Этап | План в порядке выполнения | `executionTimeMillis`, мс | `totalDocsExamined` | `totalKeysExamined` | `nReturned` |
|---|---|---|---:|---:|---:|---:|
| События сотрудника | До | `COLLSCAN → SORT` | 52 | 120 000 | 0 | 120 |
| События сотрудника | После | `IXSCAN → FETCH` | 0 | 120 | 120 | 120 |
| Ревизии диагностики | До | `COLLSCAN → SORT` | 50 | 120 000 | 0 | 12 |
| Ревизии диагностики | После | `IXSCAN → FETCH` | 0 | 12 | 12 | 12 |

- **До** `COLLSCAN` читает все документы коллекции и применяет фильтр, затем `SORT` упорядочивает совпадения. `totalKeysExamined = 0` означает, что индексы при выполнении плана не читались.
- **После** `IXSCAN` читает ключи только для значения `42`. `FETCH` загружает полные документы по этим ключам. Число просмотренных документов сократилось в 1 000 раз для событий и в 10 000 раз для ревизий. `nReturned` сохранился для обеих выборок.
- **Время** `executionTimeMillis` включает выбор и выполнение плана на сервере. MongoDB сообщает его в целых миллисекундах. Пять нулевых значений после оптимизации показывают, что время оказалось ниже разрешения этого счётчика. [Описание метрик explain](https://www.mongodb.com/docs/manual/reference/explain-results/#executionstats)
